## 3. รายละเอียดแต่ละข้อ

### OD-1 — ยืนยันว่า S2A-SERVER คือเซิร์ฟเวอร์ PDA BLISS ที่ตั้งใจไว้

1. **สิ่งที่อนุมัติ:** ยืนยันว่าเครื่องที่ตรวจแล้วคือเครื่องเป้าหมายของ CORE staging จริง
   - Windows 11 Pro, Intel i7-10700, RAM 63.7 GB
   - NVMe (C:), SATA SSD (D:), HDD (G:)
   - เป็นเครื่องที่รัน S2, PDA ONE, Payroll และ Property อยู่
2. **ข้อแนะนำ:** ยืนยัน
3. **เหตุผล:** หลักฐานมาจากตัว collector ที่รันบนเครื่องนี้โดยตรงในโหมด Administrator ตรงกับสเปกในโจทย์ทุกข้อ
   และเห็นแอปจริงครบทั้ง 22 ตัว (EP43/EP44 เคยตรวจเครื่องพัฒนาอีกเครื่องหนึ่ง ไม่ใช่เครื่องนี้)
4. **ผลกระทบต่อระบบเดิม:** ไม่มี เป็นการยืนยันอย่างเดียว
5. **ความเสี่ยงและการย้อนกลับ:** ถ้ายืนยันผิดเครื่อง แผนทั้งหมดจะใช้ไม่ได้ จึงต้องยืนยันก่อน ยังไม่มีอะไรให้ย้อนกลับ
6. **บังคับก่อน Stage B:** ใช่
7. **สิทธิ์ Admin:** ไม่ต้อง

### OD-2 — ใช้ PostgreSQL แยกชุดใหม่สำหรับ staging (พอร์ต 5433)

1. **สิ่งที่อนุมัติ:** สร้าง PostgreSQL cluster ชุดใหม่ของ staging โดยเฉพาะ
   - ใช้ไฟล์โปรแกรม PostgreSQL 18.6 ที่ติดตั้งอยู่แล้ว (ใช้แบบอ่านอย่างเดียว)
   - เก็บข้อมูลที่ `D:\pdabliss-core-staging\pgdata`
   - รับการเชื่อมต่อเฉพาะ 127.0.0.1:5433
   - ฐานข้อมูล `pdabliss_core_staging` ใช้ collation `English_United States.1252` เหมือนฐานเดิมทุกฐาน
   - ลงทะเบียนเป็น Windows Service ชื่อ `pdabliss-core-staging-pg`
2. **ข้อแนะนำ:** แยกชุดใหม่
3. **เหตุผล:**
   - PostgreSQL หลักเป็นฐานข้อมูลใช้งานจริงของ PDA ONE (`pda_one_prod`) และ Property (`pdabliss_property`)
   - ถ้าวาง staging ไว้ในชุดหลัก ต้องสร้าง role `core_*` ซึ่งมีผลกับทั้ง cluster และต้องมี login ที่สร้างฐานข้อมูลได้
     (สำหรับทดสอบกู้ backup)
   - ชื่อ role ของ CORE ตายตัว ถ้าวันหน้ามีฐาน production ของ CORE ใน cluster เดียวกัน จะใช้ role ชุดเดียวกับ
     staging ทำให้แยกสิทธิ์ไม่ได้
   - การแยกชุดทำให้ PostgreSQL หลักไม่ถูกเปลี่ยนเลยแม้แต่บรรทัดเดียว
4. **ผลกระทบต่อระบบเดิม:**
   - PDA ONE และ Property ไม่ถูกแตะ: ไม่สร้าง role ไม่แก้ `pg_hba` ไม่แก้ค่าตั้ง และไม่รีสตาร์ต PostgreSQL หลัก
   - S2, Payroll และแอปอื่นไม่เกี่ยวข้อง
   - ใช้ RAM เพิ่มราว 150–400 MB
5. **ความเสี่ยงและการย้อนกลับ:**
   - **ความเสี่ยงต่ำ:** พอร์ตชนหรือกระทบ PostgreSQL หลัก
     - ป้องกัน: ใช้พอร์ต ข้อมูล และ service แยกกัน
     - ตรวจว่า postmaster ของ PostgreSQL หลัก (PID 5764) ยังเป็นตัวเดิม
   - **ข้อควรทราบ:** เมื่ออัปเกรด PostgreSQL 18 ในอนาคต ต้องหยุด staging ก่อน
   - **ย้อนกลับ:**
     - หยุด service (R1)
     - ถ้าจะถอนออก: `pg_ctl unregister` แล้วลบโฟลเดอร์ (R4) ต้องได้อนุมัติแบบ A-8b
     - PostgreSQL หลักไม่มีอะไรต้องคืนค่า
6. **บังคับก่อน Stage B:** ใช่ เพราะแผนทั้งหมดอิงข้อนี้

   ถ้าเลือกวางในชุดหลักแทน ต้องเขียนแผนใหม่ และต้องอนุมัติการสร้าง role บนฐาน production แยกต่างหาก
7. **สิทธิ์ Admin:** ต้อง ตอนลงทะเบียนและสั่งเริ่ม service ในขั้น B3

### OD-3 — ใช้ Windows Service (ผ่าน WinSW) แทน PM2

1. **สิ่งที่อนุมัติ:** รัน backend และ frontend ของ staging เป็น Windows Service สองตัว
   - `core-staging-api` และ `core-staging-web`
   - รันด้วยบัญชีเสมือน `NT SERVICE\…` ซึ่งไม่ใช่ Admin
   - ถ้าล่ม จะรีสตาร์ตเองหลัง 10 / 30 / 60 วินาที
   - เริ่มเองหลังเปิดเครื่อง (แบบหน่วงเวลา)
   - log หมุนไฟล์ทุก 10 MB เก็บไว้ 8 ไฟล์
   - **CORE staging จะไม่ใช้ PM2 ในทุกรูปแบบ**
2. **ข้อแนะนำ:** Windows Service ผ่าน WinSW
3. **เหตุผล:** การตรวจพบว่า
   - PM2 ตัวจริงรันเป็น SYSTEM (PID 2228) โดย Scheduled Task ตอนบูต และใช้โฟลเดอร์ `.pm2` ในโปรไฟล์ผู้ใช้
   - มี PM2 daemon ของบัญชีผู้ใช้ที่ว่างอยู่อีก 3 ตัวซึ่งใช้โฟลเดอร์เดียวกัน
   - ถ้าเอา CORE ไปใส่ PM2 จะต้องสั่ง PM2 ตัวจริงในฐานะ SYSTEM และ `pm2 save` จะเขียนทับรายการกู้คืน
     (`dump.pm2`) ของแอปจริงทั้ง 23 ตัว
   - หรือต้องใส่ใน daemon ของผู้ใช้ ซึ่งจะถูกเรียกซ้ำทุกครั้งที่ล็อกอิน

   ทั้งสองทางเสี่ยงต่อแอปจริงเกินไป
4. **ผลกระทบต่อระบบเดิม:** ไม่มี
   - ไม่สั่งคำสั่ง `pm2` ใด ๆ
   - ไม่แก้ `dump.pm2`, Run key หรือ Task เดิม
   - แอปทั้ง 22 ตัวทำงานต่อตามปกติ
5. **ความเสี่ยงและการย้อนกลับ:**
   - ความเสี่ยงหลักคือความถูกต้องของไฟล์ WinSW (ดู OD-10)
   - **ย้อนกลับ:**
     - `Stop-Service` (R1)
     - ถ้าจะถอนออก: `core-staging-*.exe uninstall` (R4)
6. **บังคับก่อน Stage B:** ใช่
7. **สิทธิ์ Admin:** ต้อง ตอนติดตั้ง ตั้งบัญชี และสั่งเริ่ม service ในขั้น B5

   - **ถ้าพบ:** หยุดทันที (R1)

7. **สิทธิ์ Admin:** ไม่ต้อง

### OD-6 — ตำแหน่งข้อมูลและ backup (ปรับรอบ 2: ตรวจ S2 NAS จากของจริงแล้ว)

1. **สิ่งที่อนุมัติ:**
   - **ข้อมูล staging:** `D:\pdabliss-core-staging` บน SATA SSD
   - **backup:** เลือกด้วย **กฎตัดสินที่ C0**
     - ใช้ `G:\pdabliss-core-staging-backups` (HDD คนละดิสก์) **เมื่อผ่านทั้งสองข้อ**
       - (ก) ไฟล์ตั้งค่า S2 NAS ยังกำหนด root ทุกตัวไว้ใต้ `G:/S2_NAS_DATA/`
       - (ข) ไม่มี SMB share ที่ไม่ใช่ share ผู้ดูแลระบบ (`G$`, `C$`, `ADMIN$` …) ชี้ไปที่ `G:\` หรือโฟลเดอร์ backup
     - **ถ้าข้อใดไม่ผ่าน หรือตรวจไม่ได้ในวันนั้น** ให้ใช้ทางสำรอง `D:\pdabliss-core-staging-backups`
2. **ข้อแนะนำ:** อนุมัติกฎนี้

   **ผลการตรวจจริงวันนี้** (อ่านอย่างเดียว โดยได้รับอนุญาตเข้าถึงโฟลเดอร์ S2_NAS จากเจ้าของ)

   | แหล่ง         | สิ่งที่พบ |
   | ------------- | -------- |
   | ไฟล์ตั้งค่า    | `S2_NAS_STORAGE_ROOT = G:/S2_NAS_DATA/storage` และ root ของ backup, restore และ rehearsal อยู่ใต้ `G:/S2_NAS_DATA/backups` |
   | โค้ด          | ทุกการเข้าถึงไฟล์ผ่าน `resolveInsideStorage()` ซึ่งปฏิเสธ path ที่ออกนอก storage root และไม่มีส่วนใดไล่รายการ `G:\` |
   | build ที่รันจริง | ตรวจ `dist` ที่ใช้รันอยู่ (build เมื่อ 21 ก.ย.) ด้วย พบตัวป้องกันเดียวกัน ข้อสรุปจึงใช้กับระบบที่รันจริง ไม่ใช่แค่ซอร์ส |

   หมายเหตุ: รีโพ S2 NAS มีการแก้ไขที่ยังไม่ commit ในไฟล์ส่วน storage ซึ่งไม่ใช่ของ EP48.5 การตรวจครั้งนี้อ่านอย่างเดียวและไม่ได้แตะ

   **สรุป:** แอป S2 NAS ให้บริการเฉพาะ `G:\S2_NAS_DATA\storage` และโฟลเดอร์ backup ของ CORE อยู่นอกขอบเขตนั้น

   **อย่างไรก็ตาม จะไม่ถือว่าไดรฟ์ G: เป็นพื้นที่ส่วนตัว**
   - ทุกบัญชีและ service ในเครื่องอ่าน root ของ G: ได้
   - SMB share ยังไม่เคยถูกตรวจ และพอร์ต 445 เข้าถึงได้จาก LAN ขณะที่ Firewall ปิด

   จึงต้องตั้ง ACL ให้โฟลเดอร์ backup โดยตัดการสืบทอดสิทธิ์ ให้เฉพาะ Administrators, SYSTEM และ NetworkService
   และ collector เพิ่มการตรวจ SMB share แล้ว
3. **เหตุผล:** backup ควรอยู่คนละดิสก์กับข้อมูล การตรวจจากไฟล์ตั้งค่าและโค้ดจริงยืนยันว่าไม่ทับกับ S2 NAS
   ส่วนกฎที่ C0 ป้องกันกรณีค่าตั้งเปลี่ยน หรือมี share ที่ไม่รู้มาก่อน
4. **ผลกระทบต่อระบบเดิม:**
   - S2 NAS: ไม่เขียนใน `G:\S2_NAS_DATA`
   - PDA ONE: ไม่แตะ `D:\S2A_BACKUP`
   - ไม่แตะรีโพของโปรเจกต์อื่น
   - backup ไม่ถึง 1 MB ต่อครั้ง
5. **ความเสี่ยงและการย้อนกลับ:**
   - **ข้อจำกัดของทางสำรอง D::** backup อยู่ **SSD ลูกเดียวกับข้อมูล staging**
     - ถ้าดิสก์ D: เสียหรือโดน ransomware จะเสียทั้งข้อมูลและ backup
     - ป้องกันได้เฉพาะความเสียหายเชิงตรรกะ เช่น migration ผิดหรือข้อมูลถูกลบ
     - **รับได้เฉพาะข้อมูล demo** และ **ห้ามใช้กับ pilot** จนกว่าจะมีดิสก์แยกและสำเนานอกเครื่อง
   - **ย้อนกลับ:** การลบโฟลเดอร์ต้องได้อนุมัติแบบ A-8b ทุกครั้ง
6. **บังคับก่อน Stage B:** ใช่ ต้องตัดสินก่อน A-2
7. **สิทธิ์ Admin:** ต้อง เพื่อสร้างโฟลเดอร์และตั้ง ACL

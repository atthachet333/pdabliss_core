## 2. Implementation plan (as built)

1. Move the shared aggregates (Sales fulfilment progress + stage, PO receive progress, PR ordering) into
   `backend/src/dashboards/facts.ts`, used by EP47 and EP48 alike — one definition, any set of authorized branches.
2. `backend/src/executive/` — one read-only service built on a **work-item model** (§3), a strict response allow-list
   (`view.ts`), two GET routes. No migration, no new permission code, no write route.
3. Frontend: one lazy chunk (`features/executive/CommandCenter.tsx`) at `/core/executive` and
   `/core/executive/documents/:kind/:id`; the EP47 refresh hook moved to `features/dashboards/liveResource.ts` and shared.
4. Entry points for Owner / Executive only: CORE home button, the Executive department card, the CORE menu.

## 3. The work-item model

Every open, non-draft document becomes exactly **one** item in exactly **one** current stage (from canonical statuses
and the shared aggregates), with: the department whose document it is, the department that acts next, a class —
`BLOCKED` (a canonical condition), `OVERDUE` (past the document's own date), `MISSING_DATE` (lateness cannot be
judged), `WAITING` — evidence (codes and line / document counts) and dates. All seven areas below are views of that one
list, so no document is counted twice and every number can be traced to the documents behind it.

## 5. Ordering (deterministic, explainable)

Priority queue: BLOCKED (delivery exception → production shortage → production paused) → OVERDUE (most days overdue
first) → stock discrepancies (oldest first); ties by days in stage, then document number, then id. Bottleneck items use
the same order (class, reason, days overdue, age, number). Urgency is never derived from counts.

## 6. Access

| Who                                                                               | Command Center                                                                                           |
| --------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------- |
| Company Owner                                                                     | yes (every enabled department; still bound by tenant, branch, approval and audit rules — no write route) |
| Executive                                                                         | yes, READ-only (`readOnly: true`; the page has no action button)                                         |
| System Admin                                                                      | no (403) — administration in the Company Control Center                                                  |
| Manager / Staff / Viewer (any department, **including the Executive department**) | no (403) — their EP47 dashboard                                                                          |
| Unassigned / ambiguous                                                            | no (403)                                                                                                 |

Gate: role ∈ {Owner, Executive} **and** effective `executive.overview.view` (so a disabled Executive department or a
DENY exception closes it). Enforced on the server for every request.

## 7. Refresh and cache

Shared rules (`features/dashboards/liveResource.ts`): load on open; every 120 s only while the tab is visible; on
returning after 30 s; Refresh button; one request at a time (a new one aborts the previous); a refusal replaces the data;
a network failure keeps the last result marked stale; an answer for another scope (branch filter) is discarded; the
view is keyed by the branch filter; another CORE request's 403 triggers one re-check, never while the Command
Center's own request is out (no loop). API answers are `Cache-Control: no-store`. No WebSocket.
